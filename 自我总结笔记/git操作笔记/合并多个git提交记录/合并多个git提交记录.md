## **方法：`git reset --soft` + `git commit --amend`**

适用于合并 **未推送** 的多个提交（如最近的 2-3 个提交）。

### **步骤**

1. **查看最近的提交记录**：

   ```
   git log --oneline
   ```

   输出示例：

   ```
   abc1234 (HEAD -> main) 第三次提交
   def5678 第二次提交
   ghi9012 第一次提交
   ```

2. **软重置到要合并的最早提交的前一个提交**：

   - 如果你想合并 

     最近 3 个提交

     ，就回退到 

     ```
     HEAD~3
     ```

     ：

     ```
     git reset --soft HEAD~3
     ```

   - 如果你想合并 

     最近 2 个提交

     ，就回退到 

     ```
     HEAD~2
     ```

     ：

     ```
     git reset --soft HEAD~2
     ```

3. **检查暂存区**（确保所有更改已被暂存）：

   ```
   git status
   ```

   - 你会看到所有更改都处于 `Changes to be committed`（已暂存）。

4. **重新提交（合并所有更改为一个提交）**：

   ```
   git commit -m "合并最近的多次提交"
   ```

   - 或者使用 

     ```
     --amend
     ```

     （如果已经有提交信息）：

     ```
     git commit --amend -m "合并最近的多次提交"
     ```

5. **强制推送到远程（如果已经推送过）**：

   ```
   git push --force
   ```

   - **⚠️ 慎用 `--force`**，它会覆盖远程历史，确保没有其他人依赖这些提交。

------

## **示例（合并最近 3 个提交）**

```
# 1. 查看提交记录
git log --oneline
# 输出：
# abc1234 (HEAD -> main) 第三次提交
# def5678 第二次提交
# ghi9012 第一次提交
# jkl3456 更早的提交

# 2. 软重置到 HEAD~3（回退到 "更早的提交"）
git reset --soft HEAD~3

# 3. 检查暂存区（所有更改已暂存）
git status

# 4. 重新提交（合并 3 个提交为 1 个）
git commit -m "合并最近 3 个提交"

# 5. 强制推送（如果已经推送过）
git push --force
```

------

## **适用场景**

✅ **适合合并未推送的多次提交**（如本地测试提交、临时修复提交）。
 ✅ ​**​比 `git rebase -i` 更简单​**​，适合少量提交合并。

❌ **不适合已推送的提交**（除非你确定可以 `--force` 覆盖）。
 ❌ ​**​不适合需要精细调整提交信息的情况​**​（`git rebase -i` 更灵活）。

------

## **总结**

| 命令                      | 作用                                      |
| ------------------------- | ----------------------------------------- |
| `git reset --soft HEAD~N` | 回退到前 N 个提交，但保留所有更改到暂存区 |
| `git commit --amend`      | 修改最近一次提交（或合并暂存区的更改）    |
| `git push --force`        | 强制推送（慎用，会覆盖远程历史）          |

这样，你就可以快速合并多次提交，让 Git 历史更清晰！ 🚀



















### **用费曼的方式解释事件循环（Event Loop）**

想象你是一个忙碌的咖啡店老板（**主线程**），店里只有你一个人（**单线程**），但顾客（**任务**）源源不断。你要怎么高效处理所有订单，不让顾客等太久？

------

### **1. 同步任务：直接做的订单**

- **“一杯美式咖啡！”** → 你立刻做好递出去（**同步执行**）。
- **“再来一杯拿铁！”** → 继续做，没有拖延。
- **问题**：如果有个顾客点了一杯需要现磨的咖啡（**耗时任务**），你埋头磨豆子时，其他顾客只能干等，队伍越来越长（**页面卡死**）。

**解决办法**：把耗时任务外包（**异步处理**）！

------

### **2. 异步任务：外包的订单**

- **“我要一杯手冲咖啡，慢慢来！”** → 你记下订单（**注册回调函数**），交给后厨的咖啡师（**浏览器/Node.js 的底层线程**）处理，自己继续服务下一位顾客。
- **后厨做完后**，会把咖啡放在柜台（**任务队列**），等你有空时（**调用栈清空**）再端给顾客。

------

### **3. 事件循环：你的工作流程**

你（**主线程**）的工作方式是这样的：

1. **先处理所有直接能做的订单**（同步任务）。

2. 

   检查柜台

   （任务队列）：

   - 

     优先看“加急区”

     （

     微任务队列

     ，比如 

     ```
     Promise.then
     ```

     ）：

     - “这是您要的糖包！”（快速处理，插队优先）。

   - 

     再看普通订单区

     （

     宏任务队列

     ，比如 

     ```
     setTimeout
     ```

     ）：

     - “您的手冲咖啡好了！”（按顺序处理）。

3. **重复这个过程**，直到打烊（程序结束）。

------

### **举个栗子 🌰**

```
console.log("1. 直接做的美式咖啡"); // 同步任务

setTimeout(() => {
  console.log("4. 后厨做好的手冲咖啡"); // 宏任务
}, 0);

Promise.resolve().then(() => {
  console.log("3. 加急的糖包"); // 微任务
});

console.log("2. 直接做的拿铁"); // 同步任务
```

**输出顺序**：

```
1. 直接做的美式咖啡  
2. 直接做的拿铁  
3. 加急的糖包  
4. 后厨做好的手冲咖啡  
```

**为什么？**

- 先做完所有同步任务（1 和 2）。
- 然后检查“加急区”（微任务 3）。
- 最后处理普通订单（宏任务 4）。

------

### **关键点**

- **同步任务**：立刻执行，不拖延。
- **异步任务**：外包出去，完成后回调放入队列。
- **微任务插队**：`Promise.then` 比 `setTimeout` 优先级高。
- **事件循环**：永远在问：“现在该做什么？”（循环检查队列）。

就像经营咖啡店，**事件循环让你用单线程也能“并发”处理任务**！ ☕️

## **5. 浏览器 vs Node.js 的事件循环**

|      特性      |               浏览器               |                     Node.js                      |
| :------------: | :--------------------------------: | :----------------------------------------------: |
| **微任务队列** | `Promise.then`、`MutationObserver` | `process.nextTick`（优先级最高）、`Promise.then` |
| **宏任务队列** |      `setTimeout`、`DOM事件`       |       `setTimeout`、`setImmediate`、`I/O`        |
|  **渲染阶段**  |   有（`requestAnimationFrame`）    |                        无                        |
